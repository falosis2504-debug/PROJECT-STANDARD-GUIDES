# 03. 코딩 컨벤션

- 상태: 초안 | 버전: 0.3
- 선행: 01(기술스택), 02(명명규칙)

## 작성 방법
언어·프레임워크가 미정이므로 **언어 독립 규칙**을 이 문서에 확정하고, 언어별 세부 규칙은 8장 템플릿으로 확정 후 추가한다.
- 🔒 고정 / ✏️ 가변 / `[제안]` 확정 전 안 / `[결정 필요]` 미결정
- 규범 용어: MUST(필수) / SHOULD(권장) / MAY(선택) — 00-governance 정의 기준

- 포맷 위반은 코드 리뷰에서 논의하지 않고 **포매터/린터로 자동 처리**한다.

## 2. 주석 / 문서화
### 2.1 필수 주석 🔒
| 대상 | 필수 여부 | 내용 |
|---|---|---|
| 업무 클래스(5장 대상) 파일 | MUST | 프로그램 ID(접두부 9자), 한글명, 설명 |
| public 메서드 | MUST | 목적, 파라미터, 반환, 예외 |
| 복잡한 로직·비직관적 처리 | MUST | **왜** 그렇게 했는지 (무엇은 코드로 표현) |
| 일반 private/지역 로직 | MAY | |

- 주석 작성 언어는 **한글**, 식별자는 영문.
- 파일 머리 주석 예시 (형식은 언어별 문서화 주석으로 변환):
  ```
  프로그램ID : FRISB0001
  프로그램명 : 투자전략 컨트롤러
  설명       : 투자전략 조회/저장 API
  ```
- 이력 주석(작성자·일자 나열)은 쓰지 않는다. 변경 이력은 Git 이 관리한다.

### 2.2 금지 / 표기
- **주석 처리된 코드 커밋 금지** (삭제는 Git 으로 복원).
- 마커: `TODO(담당자, YYYY-MM-DD): 내용`, `FIXME(담당자, YYYY-MM-DD): 내용`. 담당자 없는 마커 금지.
- 마커는 릴리스 전 점검 대상이며, 장기 방치되는 TODO 는 이슈로 전환한다.

## 3. 예외 처리
### 3.1 원칙 🔒
- **빈 `catch` 금지, 예외 삼키기 금지.** 처리하지 않을 예외는 던지거나, 최소한 로그를 남기고 사유를 주석으로 적는다.
- 광범위한 예외 포착(`Exception`/`Throwable` 일괄 catch)은 최상위 처리 지점(공통 핸들러)에서만 허용한다.
- 예외를 변환할 때는 **원인(cause)을 보존**한다.
- 예외를 정상 흐름 제어에 사용하지 않는다.
- 자원(DB 연결, 스트림 등)은 반드시 해제한다. (언어의 자동 해제 구문 사용)

### 3.2 예외 구분 🔒
| 구분 | 의미 | 처리 |
|---|---|---|
| 업무 예외 | 검증 실패·업무 규칙 위반 등 예상 가능한 오류 | **에러 코드를 쓰지 않고** 응답값에 예외 데이터를 포함하여 전달(04 3.1), 로그 WARN |
| 시스템 예외 | DB·네트워크·버그 등 예상 외 오류 | 공통 핸들러에서 처리, **에러 코드(`E`+순번 4자리)** 부여, 사용자에는 일반 메시지, 로그 ERROR |

### 3.3 에러 코드·메시지 🔒
- 에러 코드는 인터페이스 ID 와 **별개의 코드 체계**(`E` + 순번 4자리, 예: `E0493`)이며 **시스템 오류에만** 부여한다. (02번 6장, 04번 5장)
- **사용자 메시지**와 **로그 메시지**를 분리한다. 사용자에게 스택트레이스·SQL·내부 경로를 노출하지 않는다.
- 메시지 문구는 코드에 하드코딩하지 않고 메시지 관리 대상으로 둔다. (관리 방식: 04-design-standard)

## 4. 로깅
### 4.1 레벨 🔒
| 레벨 | 사용 기준 | 운영 |
|---|---|---|
| ERROR | 처리 불가, 즉시 조치 필요 | 출력 |
| WARN | 복구 가능한 이상, 업무 예외 | 출력 |
| INFO | 주요 업무 이벤트(요청 시작/종료, 배치 시작/종료) | 출력 |
| DEBUG | 개발 진단 | **비활성** |

### 4.2 규칙
- `System.out`/`print`/`console.log` 등 **표준 출력으로 로그 대용 금지**. 로깅 프레임워크를 사용한다. 🔒
- 로그에는 **추적 ID(Trace ID)**, **프로그램 ID**, 처리 결과를 포함한다. 🔒
- 권장 로그 항목: 일시, 레벨, Trace ID, 프로그램 ID(예: `FRISB0001`), 사용자 ID, 메시지.
- **로그에 남기면 안 되는 정보** 🔒: 비밀번호, 인증 토큰·키, 주민등록번호, 계좌번호·카드번호 원문 등 개인정보·민감정보. 필요 시 마스킹(5.3)한다.
- 반복문 내부 대량 로그, 오류 후 같은 예외를 여러 계층에서 중복 로깅하는 것을 금지한다. (한 곳에서만 기록)
- 로그 파일 위치·로테이션·보관은 4.3 을 따른다.

### 4.3 로그 파일 위치 · 로테이션 · 보관 (중앙 수집형)
앱 서버에는 단기만 보관하고, **중앙 로그 서버(NAS/전용 스토리지)로 실시간 수집**하여 중앙에서 장기 보관한다. 🔒

| 항목 | 규칙 | 구분 |
|---|---|---|
| 앱 서버 경로 | `/logs/{시스템코드 소문자}/{환경}/{종류}.log` (예: `/logs/fr/prod/app.log`) | 🔒 |
| 중앙 경로 | `/logs-center/{시스템코드 소문자}/{환경}/{yyyy}/{MM}/{dd}/{서버명}/` | 🔒 |
| 로그 종류 | `app`(애플리케이션), `error`(에러), `access`(접속), `audit`(감사·거래) 분리 | 🔒 |
| 수집 | 수집 에이전트로 중앙 서버에 실시간 전송. 전송 실패 시 로컬에 유지 후 재전송 | 🔒 |
| 앱 서버 로테이션 | 일 단위 롤링 + 파일당 **100MB** 초과 시 분할, 롤링 파일 gzip 압축 | 🔒 |
| 앱 서버 보관 | **7일** (이후 자동 삭제, 중앙 전송 확인 후) | 🔒 |
| 중앙 보관 | 온라인 **90일** → 이후 콜드 스토리지에 보관 기간 종료까지 | 🔒 |
| 변조 방지 | 중앙 보관본은 수정·삭제 불가 권한(읽기 전용/WORM 성격)으로 보관, 접근 이력 기록 | 🔒 |
| 접근 통제 | 로그 조회 권한은 운영·감사 담당자로 제한 | 🔒 |
| 환경별 | `dev`, `stg` 는 중앙 수집 없이 로컬 보관(A안: 30일)도 허용 | 🔒 |

**로그 종류별 보관 기간** ✏️ (법정·내규 기간은 보안·준법 담당자 확인 후 프로젝트별 기록)
| 로그 종류 | 앱 서버 | 중앙 보관 (제안) | 프로젝트 확정값 |
|---|---|---|---|
| 애플리케이션/에러 로그 (`app`, `error`) | 7일 | 1년 | |
| 접속 로그 (`access`) | 7일 | 법정 기간 이상 | |
| 감사/거래 로그 (`audit`) | 7일 | 법정 기간 이상 | |

- 로그 보관 기간·방식 변경은 00-governance 의 표준 변경 절차를 따른다.
- 규모 확대로 검색·모니터링 요구가 커지면 중앙 로그 플랫폼(검색·대시보드형)으로 확장한다.

## 5. 보안 코딩
금융 서비스를 전제로 한 기본 규칙이며, 참고 기준은 행정안전부 소프트웨어 개발보안 가이드, 금융보안원 가이드, OWASP Top 10 이다.

### 5.1 입력 검증 / 인젝션 🔒
- 모든 외부 입력(요청 파라미터, 본문, 파일, 헤더)은 **서버에서 검증**한다. (클라이언트 검증은 보조)
- SQL 은 **바인딩 변수 사용 필수**. 문자열 연결로 SQL 생성 금지. 동적 정렬·테이블명 등은 허용 목록(화이트리스트)으로 제한한다.
- 출력 시 컨텍스트에 맞게 이스케이프한다. (XSS 방지) 임의 HTML 삽입 금지.
- 파일 업로드: 확장자·크기·MIME 검증, 저장 경로 고정, 파일명 원본 사용 금지.
- 경로 조작(`../`), 명령어 실행 입력 연결 금지.
- 외부 입력 URL 로의 서버 요청(SSRF)은 허용 목록으로 제한한다.

### 5.2 인증 / 인가 / 세션 🔒
- 인가 검사는 **서버에서 모든 요청마다** 수행한다. 화면 숨김만으로 제어하지 않는다.
- 비밀번호는 평문 저장·로깅 금지, 단방향 해시(솔트 포함)로 저장한다.
- 세션/토큰은 만료 시간을 두고, 로그아웃·만료 시 무효화한다.
- 데이터 접근 시 소유자(본인) 검증을 수행한다.

### 5.3 개인정보 / 민감정보 🔒
- 개인정보·금융정보는 **저장 시 암호화**, **화면·로그 출력 시 마스킹**한다. 암호화 대상 컬럼과 마스킹 규칙은 프로젝트별로 정의한다. ✏️
- 목적 외 조회·수집 금지, 필요한 컬럼만 조회한다.
- 암호화는 검증된 표준 알고리즘/라이브러리만 사용하며 **자체 구현 금지**.

### 5.4 시크릿 관리 🔒
- 비밀번호·API 키·접속 정보 등 **시크릿을 소스·설정 파일에 평문으로 커밋 금지**. 외부 설정/시크릿 저장소를 사용한다.
- `.gitignore` 로 환경별 비밀 설정 파일을 제외한다. 유출 시 즉시 폐기·재발급한다.

### 5.5 기타
- 에러 시 내부 정보 노출 금지(3.3). 운영 환경에서 디버그 모드 금지.
- 서드파티 라이브러리는 승인된 버전만 사용하고 취약점 점검 대상에 포함한다.
- 보안 점검 항목은 06-quality-test 코드 리뷰 체크리스트와 연계한다.

## 6. 트랜잭션 / 성능
| 항목 | 규칙 | 구분 |
|---|---|---|
| 트랜잭션 경계 | Service 계층에서 시작/종료. Controller·Mapper 에서 직접 제어 금지 | 🔒 |
| 트랜잭션 범위 | 외부 호출(HTTP·파일)을 트랜잭션 안에 두지 않는다 | 🔒 |
| 대용량 조회 | 목록 조회는 **페이징 필수**, 전체 건 조회 금지 | 🔒 |
| N+1 | 반복문 안에서 조회 쿼리 호출 금지, 일괄 조회로 대체 | 🔒 |
| `SELECT *` | 사용 금지, 필요한 컬럼만 명시 | 🔒 |
| 일괄 처리 | 대량 insert/update 는 배치(일괄) 처리 | 🔒 |
| 매직 넘버/문자열 | 상수 또는 공통코드로 정의 | 🔒 |

## 7. 공통 코딩 규칙
- 메서드는 한 가지 일만 하며 길이는 **50줄 이내** 권장. 중첩 깊이 3단계 이내 권장.
- 매개변수는 5개 이하 권장, 많으면 Dto 로 묶는다.
- `null` 반환보다 빈 컬렉션/명시적 결과를 선호한다.
- 중복 코드는 `common` 으로 추출하되, 업무 간 공통 사용 전 공통 코드 책임자 협의.
- 계층 간 의존 방향을 지킨다: Controller → Service → Mapper/Repository (역방향·건너뛰기 금지). (01 아키텍처 원칙과 연계)
- 하드코딩된 환경 의존 값(URL, 경로, 계정) 금지, 설정으로 분리한다.
- 날짜·시간 처리는 표준 라이브러리의 날짜 타입을 사용하고, DB 문자열 도메인(`yyyyMMdd`, `yyyyMMddHHmmss`)과의 변환은 공통 유틸로 일원화한다.
