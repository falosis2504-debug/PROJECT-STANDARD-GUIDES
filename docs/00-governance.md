# 00. 문서 거버넌스

- 상태: **확정** | 버전: 1.0

## 목표
표준 문서를 누가, 어떻게 작성·승인·변경·예외 처리하는지 정한다.
- 🔒 고정 / ✏️ 가변(프로젝트별 정의) / `[제안]` 확정 전 안 / `[결정 필요]` 미결정

## 1. 문서 관리 규칙
### 1.1 파일 · 위치 🔒
| 항목 | 규칙 |
|---|---|
| 형식 | Markdown (`.md`), UTF-8, LF |
| 위치 | 저장소의 `docs/` (표준 문서 저장 위치는 05 1장 `[결정 필요]`) |
| 파일명 | `NN-kebab-case.md`. 하위 문서는 `NN-N-kebab-case.md`, 부록은 순번 이어서 부여 |
| 변경 방식 | 문서 변경도 코드와 동일하게 **브랜치 → MR → 병합** (05) |
| 커밋 | `docs(문서번호): 내용` (예: `docs(02): 파일 명명규칙 접미사 추가`) |

### 1.2 문서 구성
| 번호 | 문서 | 성격 |
|---|---|---|
| 00 | 문서 거버넌스 (본 문서) | 운영 기준 |
| 01 | 공통 원칙·기술스택·아키텍처 | 기반 기준 |
| 02 (02-1 ~ 02-3) | 명명규칙 (DB 프로파일, 약어 사전, 인터페이스 ID) | 표준 |
| 03 | 코딩 컨벤션 | 표준 |
| 04 | 설계 표준 | 표준 |
| 05 | 형상관리·릴리스 | 표준 |
| 06 | 품질·테스트 | 표준 |
| 07 | 킥오프 체크리스트 | 적용 절차 |
| 08 | 산출물 구조 | 부록 |
- 앞 번호 문서가 뒤 번호 문서의 전제이다. 문서 간 충돌 시 **번호가 작은 문서가 우선**하고, 충돌은 변경 절차(3장)로 즉시 정리한다.

### 1.3 상태 · 버전 🔒
| 항목 | 규칙 |
|---|---|
| 상태 | `초안` → `검토` → `확정` |
| 버전 | `MAJOR.MINOR`. **확정 후 🔒 고정 규칙 변경 = MAJOR**, 보완·예시·🔒 이외 항목 추가 = MINOR |
| 변경이력 | 모든 문서 하단 `변경이력` 표에 버전·일자·작성자·내용을 기록 |
| 확정 표시 | 확정 시 저장소에 버전 태그를 부여 (예: `standards-v1.0`) |

### 1.4 표기 규칙 🔒
| 표기 | 의미 |
|---|---|
| 🔒 | 고정. 모든 프로젝트에 동일하게 적용하는 규칙 |
| ✏️ | 가변. 프로젝트 생성 시 업무 분석 후 프로젝트별로 정의하는 값 |
| `[제안]` | 확정 전 안. 확인 후 표시를 삭제하고 🔒 또는 ✏️ 로 확정 |
| `[결정 필요]` | 미결정. 결정 후 표를 채우고 표시를 삭제 |
| MUST / SHOULD / MAY | 필수 / 권장 / 선택 |

## 2. 역할과 책임
| 역할 | 지정 방법 | 책임 |
|---|---|---|
| **프로젝트 생성 계정** | 프로젝트를 생성한 계정 | **운영 배포 승인자**·**롤백 결정자**, `main` MR 승인·병합 (05) |
| **관리자 계정** | 프로젝트별 지정 ✏️ | `main`·`stage`·`develop` 직접 push 가능한 유일한 계정 (05 2.2) |
| **표준 관리자** | 프로젝트별 지정 ✏️. 별도 지정이 없으면 프로젝트 생성 계정이 겸임 | 표준 작성·변경 승인, 예외 승인, 대장(코드·약어·ID) 관리, 정기 검토 |
| **연계 아키텍트(TA)** | 프로젝트별 지정 ✏️ | **인터페이스 ID 중앙 채번**·결번 관리 (02-3) |
| **개발자** | 프로젝트 투입 인력 | 표준 준수, `develop`·`stage` MR 병합, 표준 변경 제안 |
| **보안·준법 담당자** | 프로젝트별 지정 ✏️ | 법정 로그 보관 기간·보안 기준 확인 (03 4.3, 5장) |
- 역할 지정 결과는 07 킥오프 체크리스트에 기록한다.
- 한 사람이 여러 역할을 겸임할 수 있다. **MR 작성자는 본인의 `main` MR 을 승인할 수 없다. 단, 프로젝트 생성 계정은 본인이 작성한 MR 도 승인·병합할 수 있다.** (05 4장)

## 3. 표준 변경 절차 🔒
```
변경 요청 → 영향도 검토 → 승인 → 문서 갱신(MR) → 공지/적용
```
| 단계 | 내용 | 담당 |
|---|---|---|
| 1. 변경 요청 | GitLab 이슈로 등록 (`docs` 라벨). 변경 내용·사유·영향 범위·적용 시점 기재. 요구사항 변경과 연관되면 `change` 라벨 병행 (05 8장) | 요청자 (누구나) |
| 2. 영향도 검토 | 영향받는 문서·코드·대장·산출물 식별 (예: 명명규칙 변경 → 파일명·API 대장·DB 객체) | 표준 관리자 |
| 3. 승인 | 승인 또는 반려. 🔒 고정 규칙 변경은 MAJOR 로 취급 | 표준 관리자 |
| 4. 문서 갱신 | 해당 문서와 연관 문서(참조 장 번호) 동시 수정, 변경이력 기록, MR 병합 | 표준 관리자 / 요청자 |
| 5. 공지·적용 | 팀 공지, 신규 작성분부터 적용. **기존 코드 소급 적용 여부와 기한은 변경 시 명시** | 표준 관리자 |

- 연관 문서 동시 수정이 필요한 대표 사례: 인터페이스 ID(02-3) ↔ API 대장(02 4.7), 예외 코드(04) ↔ `exception-codes.yml`, 기능코드(02 5.3) ↔ 폴더·DB 접두.
- **대장 항목(시스템·기능코드, 약어, 인터페이스 코드, 예외 코드) 추가는 문서 변경이 아니라 대장 갱신**이며 표준 관리자(인터페이스는 TA)가 승인한다. (재사용 금지, 02-3 1장)

## 4. 예외 처리 원칙 🔒
표준을 따를 수 없는 경우 **사전 승인**을 받아 예외로 처리한다.
| 항목 | 규칙 |
|---|---|
| 신청 | 사유, 대상(프로그램 ID/파일/DB 객체), 범위, 적용 기한, 대안·위험을 이슈로 등록 |
| 승인 | 표준 관리자 승인. 보안(03 5장) 관련 예외는 **보안·준법 담당자 협의 필수** |
| 기록 | **예외 대장**에 등록 (대상·조항·사유·승인자·기한·상태) |
| 표시 | 코드·스크립트에 예외 대장 번호를 주석으로 표기 |
| 만료 | 기한 도래 시 해소하거나 재승인. 재승인이 반복되면 표준 변경(3장)을 검토 |
- 급한 사정을 이유로 한 **사후 승인은 허용하지 않는다.** (핫픽스 사후 리뷰 불허와 동일 원칙, 05 6.4)
- 예외 대장 위치: 산출물 `00_프로젝트관리/04_품질_감리` (08)

## 5. 용어 정의
| 용어 | 정의 | 근거 |
|---|---|---|
| 시스템코드 | 소스 코드 체계의 시스템 식별 2자리 (예: `FR`) | 02 5.2 |
| 기능코드 | 업무(기능) 식별 2자리. 파일·URL·DB 에 공통 사용 (예: `IS`). 공통은 `CM` | 02 5.3 |
| 접두부 | `시스템2 + 기능2 + 계층1 + 일련번호4` 9자 (예: `FRISB0001`) | 02 5.1 |
| 프로그램 ID | 접두부 9자. 대장은 접두부 + 접미사 단위로 관리 | 02 6장 |
| 계층(P/B/D/U) | 프레젠테이션/비즈니스/데이터/통합 | 02 5.4 |
| 접미사 | 파일 역할 구분 (`Controller`, `Service`, `Dto`, `Mapper` 등) | 02 5.5 |
| 기능명 | API URL 마지막 요소 `{동사}{Target}` (예: `selectUserStrategy`) | 02 4.3 |
| 인터페이스 ID | 소스 체계와 별개 체계의 16자리 연계 식별자 (`IF…`) | 02-3 |
| 업무코드(3자리) | 인터페이스 ID 전용 업무 분류. 기능코드와 별개 | 02-3 |
| 에러 코드 | `E`+순번 4자리. **시스템 오류 전용** | 04 5장 |
| 예외 코드 | `도메인_상황`. 업무 예외용, `exception-codes.yml` 관리 | 04 3.1.1 |
| 대장 | 코드·ID·산출물을 관리하는 목록 (프로그램 ID·API·인터페이스·공통코드·예외 코드·결함·예외) | 08 |
| 반자동 배포 | 병합 후 개발자가 배포 시작 버튼을 눌러 빌드·도커 배포·재기동 | 05 6.1 |

## 7. 정기 검토 🔒
- 표준 문서는 프로젝트 단계 종료 시 관리자가 `[제안]`·`[결정 필요]` 잔여 항목과 예외 대장을 검토하고 필요 시 변경 절차(3장)로 개정한다.
- 언어·프레임워크·DBMS 확정(01) 시 기술 종속 항목(03 8장, 02-1 등)을 보완하고 버전을 갱신한다.
