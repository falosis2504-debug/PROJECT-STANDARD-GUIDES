## 3. API 설계
명명·URL·메서드·기능명은 02 4장을 따른다. (`GET`/`POST` 만, `/api/{기능코드2}/{기능명}`)

### 3.1 공통 응답 포맷 🔒
```json
{
  "success": true,
  "code": "OK",
  "message": "",
  "traceId": "20261125-0001",
  "data": {},
  "exception": null
}
```
| 필드 | 의미 | 비고 |
|---|---|---|
| `success` | 업무 처리 성공 여부 | boolean |
| `code` | 성공 `OK`, 업무 예외는 `도메인_상황` 키(예: `COMMON_INVALID_INPUT`, 3.1.1), 시스템 오류는 에러 코드(예: `E0493`, 5장) | |
| `message` | 사용자 표시 메시지 (로그용 상세 내용 제외, 03 3.3) | |
| `traceId` | 추적 ID (03 4.2 로그와 동일 값) | |
| `data` | 응답 본문. 단건은 객체, 목록은 `{대상}List` | |
| `exception` | **업무 예외 데이터**. 업무 예외가 없으면 `null`. 구조는 3.1.1 | |

- 응답 JSON 필드명은 코드 필드와 같은 **camelCase** 이며 DB 컬럼 매핑 규칙(02 2장)을 따른다. 🔒
- 날짜·시간은 DB 도메인 형식(`yyyyMMdd`, `yyyyMMddHHmmss`)을 그대로 사용한다. 🔒

### 3.1.1 업무 예외 데이터 🔒
업무 예외(검증 실패·업무 규칙 위반)는 **에러 코드(`E`+순번)를 부여하지 않고** 응답값의 `exception` 에 예외 데이터를 포함한다.
구조는 **RFC 표준 메타데이터(RFC 9457 Problem Details 의 `type`·`detail`·`instance`)** 에 프론트엔드 UI 처리를 위한 `errors` 배열을 결합한 형태이다.

```json
{
  "success": false,
  "code": "COMMON_INVALID_INPUT",
  "message": "입력값을 다시 확인해주세요.",
  "traceId": "20261125-0001",
  "data": null,
  "exception": {
    "type": "ValidationException",
    "detail": "2 fields failed validation",
    "instance": "/api/is/saveUserStrategy",
    "errors": [
      {
        "field": "email",
        "rejectedValue": "test@",
        "reason": "INVALID_EMAIL_FORMAT",
        "message": "올바른 이메일 형식이 아닙니다."
      },
      {
        "field": "age",
        "rejectedValue": 15,
        "reason": "UNDER_MINIMUM_AGE",
        "message": "만 19세 이상만 가입할 수 있습니다."
      }
    ]
  }
}
```
| 필드 | 의미 |
|---|---|
| `code` | 예외의 `도메인_상황` 키. `UPPER_SNAKE_CASE` (예: `COMMON_INVALID_INPUT`) |
| `message` | 사용자 표시용 요약 메시지 |
| `exception.type` | 예외 유형 이름 (예: `ValidationException`) |
| `exception.detail` | 예외 상세 설명(개발·운영 확인용 요약, 내부 정보 비노출) |
| `exception.instance` | 예외가 발생한 요청 URL (02 4장 형식 `/api/{기능코드2}/{기능명}`) |
| `exception.errors[]` | 필드별 오류 목록. UI 에서 필드 단위 표시에 사용 |
| `errors[].field` | 오류 필드명 (요청 JSON 필드명, camelCase) |
| `errors[].rejectedValue` | 거부된 입력값 |
| `errors[].reason` | **필드별 사유 코드** (`UPPER_SNAKE_CASE`, 예: `MIN_VALUE`, `NOT_BLANK`, `INVALID_EMAIL_FORMAT`) |
| `errors[].message` | 필드 오류 메시지(사용자 표시용) |

**키 체계**
- 예외 코드: `{도메인}_{상황}` — 예: `COMMON_INVALID_INPUT`. 도메인은 `COMMON`(공통) 또는 업무 도메인 약어(02-2 사전 약어, 프로젝트별 ✏️).
- 필드 사유 코드: 상황을 나타내는 `UPPER_SNAKE_CASE` — 예: `MIN_VALUE`, `NOT_BLANK`, `INVALID_EMAIL_FORMAT`, `UNDER_MINIMUM_AGE`.
- 예외 코드·사유 코드의 메시지는 메시지 파일(5.2)에서 키로 관리하며 문구를 하드코딩하지 않는다.

**규칙**
- 업무 예외는 HTTP 200 으로 응답하고 `success: false` 와 `exception` 으로 구분한다. (3.2)
- `rejectedValue` 에 **비밀번호·주민등록번호 등 민감정보 원문을 담지 않는다.** 해당 필드는 값을 비우거나 마스킹한다. (03 5.3)
- `errors` 는 필드와 무관한 업무 예외일 때 비어 있을 수 있다. (이 경우 `field` 대신 `message` 로 표현)
- **예외 코드(`도메인_상황`)·필드 사유 코드·도메인 약어 목록은 프로젝트별로 생성**하고, YAML 파일 등으로 **프로젝트 폴더에 별도 관리**한다. (파일명 예: `exception-codes.yml` [제안]) ✏️
```yaml
# exception-codes.yml 예시
COMMON_INVALID_INPUT:
  message: "입력값을 다시 확인해주세요."
reasons:
  NOT_BLANK: "필수 입력 항목입니다."
  MIN_VALUE: "최소값 이상이어야 합니다."
```

### 3.2 HTTP 상태코드 🔒
| 상황 | HTTP | body |
|---|---|---|
| 업무 처리 결과(성공/업무 예외) | 200 | `success` + `code` + `exception` 으로 구분 |
| 인증 실패 | 401 | 공통 응답 포맷 |
| 인가 실패 | 403 | 공통 응답 포맷 |
| 시스템 오류 | 500 | 공통 응답 포맷, 상세 내용 비노출 (03 3.3) |
- 업무 예외를 4xx 로 매핑하지 않는다. (`GET`/`POST` 만 사용하는 인프라·WAF 환경을 고려)

### 3.3 요청 공통
| 항목 | 규칙 | 구분 |
|---|---|---|
| 목록 조회 요청 | `pageNo`, `pageSize` (페이징 필수, 03 6장) | 🔒 |
| 목록 조회 응답 | `data.{대상}List`, `data.totalCnt` | 🔒 |
| 중복 요청 방지 | 등록·실행(`insert`·`save`·`execute` 등)은 **중복 제출 방지 키** 사용 | 🔒 |
| 인증 방식 | **세션 기반 인증** (서버 세션). 만료·무효화는 03 5.2 | 🔒 |
| 문서화 | API 대장(02 4.7)을 기준 문서로 하고, 별도 명세 도구는 [결정 필요] | [결정 필요] |

## 4. 공통코드
공통코드 **그룹 ID 체계는 프로젝트별로 정의**한다. (02 6.1) 이 장은 구조와 운영 방식만 정한다.

### 4.1 구조 🔒
| 테이블 | 용도 | 주요 컬럼 |
|---|---|---|
| `TB_CM_CD_GRP_C` | 공통코드 그룹 | `CD_GRP_ID`, `CD_GRP_NM`, `USE_YN`, 감사 컬럼 |
| `TB_CM_CD_DTL_C` | 공통코드 상세 | `CD_GRP_ID`, `CD`, `CD_NM`, `CD_SEQ`, `USE_YN`, 감사 컬럼 |
- 기능코드 `CM`(공통) 소속이며 유형 `C`(코드) 테이블이다. 코드 값 도메인은 02-1 (`_CD`: `VARCHAR2(10)`, `_DV_CD`/`_STTS_CD`: `VARCHAR2(4)`).

### 4.2 운영 규칙
- 코드 값은 **의미 없는 코드(문자/숫자)** 로 정의하고 의미는 `CD_NM` 으로 관리한다. 🔒
- 코드 값을 소스에 **하드코딩하지 않는다.** 소스에서는 상수/enum 으로 정의하여 사용한다. (03 6장 매직 넘버 금지) 🔒
- 코드 값 삭제 금지, 사용 중지는 `USE_YN = 'N'`. 🔒
- 조회 빈도가 높은 공통코드는 캐시 대상으로 하고 변경 시 갱신 절차를 정의한다.
- 그룹/코드 대장은 그룹 ID 부여 후 등록하며, 변경은 표준 변경 절차(00)를 따른다.

## 5. 에러 코드 / 메시지
### 5.1 코드 체계 🔒
```
예) E0493
```
| 구성 | 규칙 |
|---|---|
| 형태 | 영문 `E` + **순번 4자리** (예: `E0493`) |
| 적용 범위 | **시스템 오류 전용**. 업무 예외에는 부여하지 않음 (3.1.1) |
| 관리 | **인터페이스 ID·프로그램 ID 와 별개로 독립 관리** |
| 채번 | 중앙 관리, 발급된 코드는 재사용 금지 🔒 |
| 상세 체계 | `W`(경고)·`I`(안내) 등 구분 문자 사용 여부, 순번 대역(공통/업무별) 구분은 **별도 정의 예정** [결정 필요] |
- 시스템 공통 오류(인증·인가·시스템 오류 등)의 코드 대역은 상세 체계 정의 시 함께 확정한다. [결정 필요]

### 5.2 메시지 관리 (파일 방식)
메시지는 DB 테이블이 아닌 **YAML 등 설정 파일**로 관리한다. 🔒
| 항목 | 규칙 | 구분 |
|---|---|---|
| 저장 | 메시지 파일(YAML 등). 환경별로 분리하지 않고 소스와 함께 버전 관리 | 🔒 |
| 파일 구성 | 공통 `messages-cm.yml`, 업무별 `messages-{기능코드 소문자}.yml` | [제안] |
| 키 | 시스템 오류는 에러 코드(`E0493`), 업무 예외는 예외 코드(`COMMON_INVALID_INPUT`)와 필드 사유 코드(`MIN_VALUE`)를 키로 사용 (3.1.1) | 🔒 |
| 사용 | 코드에 문구 하드코딩 금지, **메시지 코드로만 참조** (03 3.3) | 🔒 |
| 사용자 메시지 | 사용자가 취해야 할 조치를 포함, 내부 정보 비노출 | 🔒 |
| 로그 메시지 | 03 4장 기준, 사용자 메시지와 별도 관리 | 🔒 |
| 언어 | **한국어 단일** 유지. 다국어는 적용하지 않음 | 🔒 |
```yaml
# messages-cm.yml 예시
"E0493": "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해 주세요. 계속되면 관리자에게 문의하세요."
```
- 메시지 코드 대장 항목: 메시지 코드, 구분, 사용자 메시지, 발생 조건, 조치 방법, 관련 프로그램 ID. 메시지 파일과 대장은 코드 기준으로 일치해야 한다.
- 메시지 수정 시에도 코드 변경 없이 파일만 변경하되, 표준 변경 절차(00)와 배포 절차(05)를 따른다.

## 6. 화면 설계
### 6.1 식별 / 구조
- 화면 ID = 프론트 계층 접두부 9자 (02 6장). 예: `FRISP0100`. 파일은 02 5.5(`P` 팝업·`M` 메인·`C` 컴포넌트)·5.7 폴더 규칙을 따른다. 🔒
- 일련번호는 상위 2자리(중분류) + 하위 2자리(소분류) 구조를 따른다. (02 5.1.1) 🔒

### 6.2 화면 설계서 항목
화면 ID/명, 업무(기능코드)/메뉴 경로, 화면 설명, 레이아웃(영역 구분), 항목 정의(항목명·필드명·타입·필수·검증·마스킹), 이벤트(버튼·조회·저장 동작), 호출 API(02 4.7 대장의 URL), 사용 공통코드 그룹, 권한(메뉴/버튼), 오류 메시지 코드.

### 6.3 화면 공통 기준 🔒
소규모 프로젝트에서 가장 널리 쓰이는 방식으로 선정한다.
| 항목 | 기준 |
|---|---|
| 공통 레이아웃 | **상단 헤더(로고·사용자·로그아웃) + 좌측 메뉴(LNB) + 콘텐츠 영역** |
| 화면 구성 순서 | 제목/경로(브레드크럼) → 조회 조건 영역 → 결과(목록) 영역 → 상세/입력 영역 |
| 조회 영역 버튼 | 조회 영역 우측 정렬: `[조회]` `[초기화]` |
| 결과 영역 버튼 | 결과 영역 우측 상단 정렬: `[등록]` `[저장]` `[삭제]` `[엑셀]` (필요한 것만 노출) |
| 팝업 버튼 | 하단 중앙: `[확인]`(저장) `[닫기]` |
| 버튼 명칭 | 동사 사전(02 4.3)과 대응: 조회·등록·저장·삭제 등. 임의 문구 사용 금지 |
| 필수 항목 | 라벨 앞/뒤에 `*` 표기(빨간색) |
| 입력 검증 표시 | 필드 단위로 입력란 아래 오류 메시지 표시 + 저장 시 첫 오류 필드에 포커스. 메시지는 메시지 코드로 관리(5.2) |
| 삭제/저장 확인 | 삭제는 확인 대화상자 필수 |
| 목록 | 페이징 필수(기본 20건, 10/20/50/100 선택), 컬럼 헤더 클릭 정렬, 건수 표시 |
| 빈 결과 | "조회된 데이터가 없습니다." 문구 표시 |
| 마스킹 표시 | 주민등록번호 뒷 7자리, 계좌·카드번호 중간 자리, 이름 가운데 글자, 휴대폰 중간 4자리를 `*` 처리. 해제는 권한자에 한해 사유 기록 후 허용 (03 5.3) |
- 마스킹 대상 항목과 해제 권한은 프로젝트별로 정의한다. ✏️

## 7. 인터페이스(연계) 설계
- 인터페이스는 **본 프로젝트 소스 체계와 별개의 시스템**으로 보며, 인터페이스 ID 는 **02-3 (16자리: `IF`+송신+수신+유형+업무+일련번호)** 를 따른다. 에러 코드(5장)와는 별개로 관리한다. 🔒
- 인터페이스는 **중앙 통제 채번**이며 결번(폐기)은 재사용하지 않는다. (02-3 1장)
- 연계 대상 시스템·업무 코드는 02-3 코드표(3.1, 3.3)에 프로젝트별로 정의한다. 인터페이스 업무코드(3자리)와 기능코드(2자리)는 별개이다. ✏️
- 처리유형: 동기(`O`) / 비동기(`A`) / 배치(`B`) / 파일(`F`). 유형별 전문 구조·재처리·장애 대응 기준은 연계 대상이 정해질 때 정의한다. [결정 필요]
- 인터페이스 대장 양식은 02-3 6장, 보관 위치는 08 참조.
