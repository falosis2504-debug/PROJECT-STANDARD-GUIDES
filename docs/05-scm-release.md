## 작성 방법
소규모 SI 프로젝트에서 가장 많이 쓰는 **Git Flow 간소화(main / develop / feature / hotfix)** 방식으로 정한다.
- 🔒 고정 / ✏️ 가변 / `[제안]` 확정 전 안 / `[결정 필요]` 미결정
- 도구(Git 호스팅·CI/CD)가 미정이므로 **도구 독립 규칙**을 정한다.

| 산출물 | 산출물(분석·설계·테스트 문서)은 별도 문서 저장소에서 관리 (08) | 🔒 |

## 2. 브랜치 전략
```
main     ──●───────────────●────── 운영 배포본 (태그 vX.Y.Z)
            \             /
develop  ────●──●──●──●──●──────── 통합 개발 (dev 환경)
              \    /
feature/*      ●──●                기능 개발
hotfix/*  (main 에서 분기 → main + develop 병합)
```
| 브랜치 | 용도 | 분기 원본 | 병합 대상 | 직접 push |
|---|---|---|---|---|
| `main` | 운영 배포본. 항상 배포 가능 상태 | - | - | **금지** |
| `develop` | 통합 개발. dev 환경 배포 기준 | `main` | `main` (릴리스 시) | **금지** |
| `feature/*` | 기능 개발·개선 | `develop` | `develop` | 허용(본인 브랜치) |
| `release/*` | 릴리스 준비·검증(stg). 소규모는 생략 가능 | `develop` | `main`, `develop` | 버그 수정만 |
| `hotfix/*` | 운영 긴급 수정 | `main` | `main`, `develop` | 허용(본인 브랜치) |

### 2.1 브랜치 이름 🔒
`{유형}/{이슈번호}-{kebab-case-설명}` — 영문 소문자·숫자·`-` 만 사용.
- 예: `feature/123-strategy-select`, `hotfix/130-login-session`, `release/1.2.0`
- 프로그램 ID(접두부 9자)가 정해진 작업은 설명 앞에 소문자로 붙일 수 있다. 예: `feature/123-frisb0001-strategy-select` [제안]

### 2.2 브랜치 보호 🔒
- `main`, `develop`: 직접 push 금지, force push 금지, 삭제 금지.
- 병합은 **PR 로만** 수행하고, CI 통과와 승인 1인 이상을 필수 조건으로 한다.
- `feature/*` 는 병합 후 삭제한다. 브랜치 수명은 **2주 이내** 권장하며, 길어지면 develop 을 정기적으로 병합(merge/rebase)해 충돌을 줄인다. [제안]

## 3. 커밋 메시지
```
<type>(<scope>): <제목>

<본문: 무엇을/왜 (선택)>

Refs: #이슈번호
```
| 항목 | 규칙 | 구분 |
|---|---|---|
| type | `feat` 기능 / `fix` 버그 / `docs` 문서 / `style` 포맷 / `refactor` 리팩터링 / `test` 테스트 / `chore` 기타 / `build` 빌드 / `ci` CI / `revert` 되돌림 | 🔒 |
| scope | **프로그램 ID 접두부** 또는 기능코드. 예: `FRISB0001`, `IS`, `DB` | 🔒 |
| 제목 | 한글, 명령형/현재형 간결하게, 50자 이내 권장, 마침표 없음 | 🔒 |
| 본문 | 변경 이유·영향 범위. 줄 길이 72자 권장 | [제안] |
| 이슈 연결 | `Refs: #번호` 또는 `Closes: #번호` | 🔒 |
| 단위 | 하나의 커밋은 하나의 논리적 변경. 포맷 변경과 기능 변경을 섞지 않는다 | 🔒 |

- 예: `feat(FRISB0001): 투자전략 조회 API 추가` / `fix(IS): 목록 페이징 오류 수정`
- DB 스크립트 변경은 `scope` 를 `DB` 로 하고 파일 버전을 제목에 포함한다. 예: `feat(DB): V1.0.3 투자전략 테이블 추가`
- 커밋 전 03 의 포맷·린터 검사를 통과해야 한다. 시크릿이 포함되지 않았는지 확인한다.

## 4. 코드 리뷰 / 병합 (PR)
| 항목 | 규칙 | 구분 |
|---|---|---|
| PR 필수 | `develop`, `main` 으로의 모든 변경 | 🔒 |
| 승인 | 승인자 **1인 이상** (작성자 본인 제외). 보안·DB 스키마 변경은 지정 리뷰어 포함 | 🔒 |
| 셀프 병합 | 금지 (작성자가 승인 없이 병합 불가) | 🔒 |
| CI | 빌드·린트·테스트 통과 필수 (7장) | 🔒 |
| 병합 방식 | `feature → develop`: **Squash merge** / `develop → main`, `hotfix → main`: **Merge commit(no-ff)** | [제안] |
| PR 크기 | 변경 400줄 이내 권장. 초과 시 분할 | [제안] |
| 리뷰 기한 | 요청 후 **1영업일 이내** 1차 리뷰 | [제안] |
| 리뷰 기준 | 06 코드 리뷰 체크리스트 | 🔒 |
| 충돌 해소 | 작성자가 해소 후 재요청 | 🔒 |

**PR 템플릿 항목**: 변경 요약 / 관련 이슈 / 대상 프로그램 ID / 변경 유형 / 테스트 결과 / DB 변경 여부(스크립트·롤백) / 설정 변경 여부 / 체크리스트(03 린트, 시크릿 없음, 06 리뷰 항목).

## 5. 버전 / 릴리스
| 항목 | 규칙 | 구분 |
|---|---|---|
| 버전 규칙 | `MAJOR.MINOR.PATCH` (SemVer). MAJOR 호환 불가 변경 / MINOR 기능 추가 / PATCH 버그 수정 | 🔒 |
| 태그 | `main` 에서만 `v{MAJOR}.{MINOR}.{PATCH}` (예: `v1.2.0`) | 🔒 |
| 릴리스 단위 | 릴리스 번들 = 소스 태그 + DB 스크립트 버전 + 설정 변경 목록 | 🔒 |
| 릴리스 노트 | 커밋 type 기준(`feat`/`fix`)으로 정리. 포함: 변경 기능, 프로그램 ID, 이슈, DB 변경, 영향 범위, 알려진 이슈 | 🔒 |
| 변경 이력 | `CHANGELOG` 를 릴리스 시 갱신 | [제안] |
| 배포 주기 | 프로젝트별 정의 (예: 정기 릴리스 일정) | ✏️ |

## 6. 환경 / 배포
### 6.1 환경 ↔ 브랜치
| 환경 | 약어 | 배포 기준 | 배포 방식 | 승인 |
|---|---|---|---|---|
| 개발 | dev | `develop` 병합 시 | 자동 [제안] | 불필요 |
| 스테이징(검증) | stg | `release/*` (생략 시 `develop` 의 릴리스 후보) | 수동 트리거 | 개발 리더 |
| 운영 | prod | `main` 의 **태그** | 수동, 승인 후 | **운영 배포 승인자** [결정 필요] |
- 환경별 설정값은 소스에서 분리하고 시크릿은 저장소에 두지 않는다. (03 5.4)
- 동일 산출물(빌드 결과)을 stg 에서 검증하고 **같은 산출물을 prod 에 배포**한다. 환경별 재빌드 금지. [제안]

### 6.2 운영 배포 절차 🔒
1. 릴리스 후보 확정 → 릴리스 노트·DB 스크립트·롤백 계획 준비
2. stg 배포 및 검증 (06 테스트 기준 충족, 인수 확인)
3. 배포 승인 (승인자 확인, 배포 일정 공지)
4. `main` 병합 및 버전 태그 생성
5. prod 배포 (배포 윈도우 준수), 사후 점검(헬스체크, 로그 모니터링)
6. 배포 결과 기록·공유, `develop` 과 `main` 동기화 확인

**배포 전 체크리스트**
- [ ] CI 전 단계 통과, 정적분석(시큐어코딩) 차단 이슈 없음
- [ ] DB 스크립트 검토 완료, **롤백 스크립트 준비**
- [ ] 설정 변경 목록 확인, 시크릿 반영 확인
- [ ] 영향 범위 공지, 롤백 담당자 지정
- [ ] 배포 윈도우: 프로젝트별 정의 ✏️

### 6.3 롤백 🔒
| 항목 | 규칙 |
|---|---|
| 롤백 기준 | 배포 후 사전 정의한 시간 내 치명 결함·장애 발생, 헬스체크 실패 |
| 소스 롤백 | 직전 안정 태그를 재배포 (`revert` 로 main 정정은 별도 PR) |
| DB 롤백 | 스키마 변경은 **롤백 스크립트를 릴리스와 함께 준비**. 데이터 변경(DML)은 사전 백업 후 적용 |
| 결정 권한 | 롤백 결정자: 운영 배포 승인자 또는 지정 대리인 [결정 필요] |
| 사후 | 원인 분석 및 재발 방지 기록, 필요 시 hotfix 진행 |

### 6.4 핫픽스 🔒
- `main` 의 최신 태그에서 `hotfix/*` 분기 → 수정 → PR(승인 1인) → `main` 병합 + 태그(PATCH 증가) → `develop` 병합.
- 긴급 시에도 PR·CI 를 생략하지 않는다. (사후 리뷰 허용 범위는 [결정 필요])

## 7. CI/CD 파이프라인 (도구 독립)
| 단계 | 내용 | 실패 시 |
|---|---|---|
| 1. 빌드 | 의존성 해석, 컴파일/번들 | 병합 차단 |
| 2. 린트·포맷 | 03 1장 포매터/린터 | 병합 차단 |
| 3. 단위 테스트 | 06 기준 (커버리지 목표는 06) | 병합 차단 |
| 4. 정적분석·시크릿 검사 | 시큐어코딩 점검(03 5장), 시크릿 유출 검사 | 병합 차단 |
| 5. 패키징 | 배포 산출물 생성, 버전 부여 | |
| 6. 배포 | 6.1 환경 규칙대로 dev 자동, stg/prod 수동 | |
- PR 마다 1~4단계를 실행하고, `develop`/`main` 병합 후 5~6단계를 실행한다.
- CI/CD 도구 선정은 기술 스택 확정 후 [결정 필요].

## 8. 이슈 관리
| 항목 | 규칙 | 구분 |
|---|---|---|
| 이슈 유형(라벨) | `feature`(기능) / `bug`(결함) / `change`(요구사항 변경, CR) / `docs` / `chore` | [제안] |
| 우선순위 | `P1` 긴급(운영 장애) / `P2` 높음 / `P3` 보통 / `P4` 낮음 | [제안] |
| 상태 | 신규 → 진행 → 리뷰 → 검증 → 완료 (반려/보류) | [제안] |
| 연결 | 모든 브랜치·커밋·PR 은 이슈 번호와 연결 | 🔒 |
| 요구사항 변경 | `change` 이슈는 요구사항변경요청서(CR, 산출물 `00_03`)와 연결 | 🔒 |
| 결함 | 테스트 결함은 결함관리대장(06, 산출물 `04_01/99`)과 이슈 번호 연계 | 🔒 |
- 이슈 관리 도구는 [결정 필요].
