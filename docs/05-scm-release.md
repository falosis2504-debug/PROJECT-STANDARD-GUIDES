## 1. 저장소 구성
| 항목 | 규칙 | 구분 |
|---|---|---|
| 저장소 분리 | **프론트엔드와 백엔드는 별도 저장소**로 분리한다. 각 저장소가 이 문서의 브랜치·태그·배포 규칙을 독립적으로 적용한다 | 🔒 |
| 저장소 이름 | 프로젝트별 정의 (프론트·백엔드 구분이 드러나게) | ✏️ |
| 소스 저장소 내용 | 소스·설정·DB 스크립트(`V{버전}__{설명}.sql`, 백엔드)를 관리 | 🔒 |
| 표준 문서(`docs/`) | **`docs/` 폴더**에서 관리한다 (표준 문서는 한 저장소에만 둔다) | 🔒 |
| 산출물 | 분석·설계·테스트 문서는 별도 문서 저장소에서 관리 (08) | 🔒 |
| 커밋 금지 | 시크릿(03 5.4), 빌드 산출물, 로컬 설정, 대용량 바이너리 | 🔒 |
| 필수 파일 | `README`, `.gitignore`, `.editorconfig`, MR(PR) 템플릿, 이슈 템플릿 | 🔒 |

### 1.1 프론트·백엔드 연계 🔒
- 프론트·백엔드가 함께 바뀌는 작업은 **이슈 1개**를 양쪽 저장소의 브랜치·MR 에 연결한다.
- API 변경은 하위 호환을 유지하고 **백엔드를 먼저 배포**한 뒤 프론트를 배포한다.
- 각 저장소의 릴리스 노트에 호환되는 상대 저장소 버전(태그)을 기재한다.

## 2. 브랜치 전략
```
main      ──●────────────────────●───  운영 (prod)   태그 vX.Y.Z
             ↑                    ↑
stage     ──●────●───────────────●───  스테이지 (stg)
              ↑      ↑
develop   ────●──●───●──●──●──────────  통합 개발 (dev)
               ↑  ↑
feature/* ─────●──●
hotfix/*   main 에서 분기 → main(승인) → stage, develop 역병합
```
**승격 경로: `feature/*` → `develop` → `stage` → `main`**

| 브랜치 | 용도 | 환경 | 분기 원본 | 병합 대상 |
|---|---|---|---|---|
| `main` | 운영 배포본. 항상 배포 가능 상태. 운영은 이 브랜치 하나로 관리 | prod | - | - |
| `stage` | 스테이지(검증). 운영 반영 전 검증용 | stg | `main` | `main` |
| `develop` | 통합 개발 | dev | `main` | `stage` |
| `feature/*` | 기능 개발·개선 | - | `develop` | `develop` |
| `hotfix/*` | 운영 긴급 수정 | - | `main` | `main` (이후 `stage`, `develop` 역병합) |

### 2.1 브랜치 이름 🔒
`{유형}/{이슈번호}-{kebab-case-설명}` — 영문 소문자·숫자·`-` 만 사용.
- 예: `feature/123-strategy-select`, `hotfix/130-login-session`
- 프로그램 ID(접두부 9자)가 정해진 작업은 설명 앞에 소문자로 붙일 수 있다. 예: `feature/123-frisb0001-strategy-select` 

### 2.2 브랜치 보호 🔒
| 브랜치 | 직접 push | force push / 삭제 | 병합 | 승인 |
|---|---|---|---|---|
| `main` | **관리자 계정만** | 금지 | 개발자 병합 불가. MR 승인 후 운영 배포 승인자가 병합 | **필수** (4장) |
| `stage` | **관리자 계정만** | 금지 | 개발자가 MR 로 병합 가능 | 불필요 (CI 통과 필요) |
| `develop` | **관리자 계정만** | 금지 | 개발자가 MR 로 병합 가능 | 불필요 (CI 통과 필요) |
| `feature/*`, `hotfix/*` | 허용(본인 브랜치) | 본인 브랜치만 허용 | - | - |
- **개발자는 `main`, `stage`, `develop` 에 직접 push 할 수 없다.** 개발자가 할 수 있는 병합은 `develop`, `stage` 로의 MR 병합뿐이다. 🔒
- `feature/*` 는 병합 후 삭제한다. 브랜치 수명·크기에 별도 제한은 두지 않는다.

## 3. 커밋 메시지
```
<type>(<scope>): <제목>

<본문: 무엇을/왜 (선택)>

Refs: #이슈번호
```
| 항목 | 규칙 | 구분 |
|---|---|---|
| type | `feat` 기능 / `fix` 버그 / `docs` 문서 / `style` 포맷 / `refactor` 리팩터링 / `test` 테스트 / `chore` 기타 / `build` 빌드 / `ci` CI / `revert` 되돌림 | 🔒 |
| scope | **프로그램 ID 접두부** 또는 기능코드. 예: `FRISB0001`, `IS`, `DB` | 🔒 |
| 제목 | 한글, 간결하게, 50자 이내 권장, 마침표 없음 | 🔒 |
| 본문 | 변경 이유·영향 범위. 줄 길이 72자 권장 | 🔒 |
| 이슈 연결 | `Refs: #번호` 또는 `Closes: #번호` | 🔒 |
| 단위 | 하나의 커밋은 하나의 논리적 변경. 포맷 변경과 기능 변경을 섞지 않는다 | 🔒 |

- 예: `feat(FRISB0001): 투자전략 조회 API 추가` / `fix(IS): 목록 페이징 오류 수정`
- DB 스크립트 변경은 `scope` 를 `DB` 로 한다. 예: `feat(DB): V1.0.3 투자전략 테이블 추가`
- 커밋 전 03 의 포맷·린터 검사를 통과해야 한다. 시크릿이 포함되지 않았는지 확인한다.

## 4. 병합 / 코드 리뷰 (MR·PR)
| 항목 | 규칙 | 구분 |
|---|---|---|
| 병합 방식 | **항상 Merge commit** 만 사용한다. (Squash·Rebase merge 금지, fast-forward 도 merge commit 을 생성) | 🔒 |
| 승인 기준 | **`main` 으로의 병합에만 적용**한다. 승인자는 **운영 배포 승인자**(프로젝트 생성 계정, 6.1) | 🔒 |
| `develop`, `stage` 병합 | 승인 불필요. **개발자가 MR 로 병합**하며 CI 통과 필수. 직접 push 는 불가(관리자 계정만 가능) | 🔒 |
| 셀프 병합 | `main` 은 개발자가 병합할 수 없고, 승인 후 운영 배포 승인자가 병합. 작성자 본인은 자기 MR 을 승인할 수 없으나 **프로젝트 생성 계정은 본인이 작성한 MR 도 승인·병합 가능** | 🔒 |
| 리뷰 기준 | `main` 승인 시 06 코드 리뷰 체크리스트 | 🔒 |
| 충돌 해소 | 작성자가 해소 후 재요청 | 🔒 |
- MR 크기·리뷰 기한 등 별도 제한은 두지 않는다.
- `main` 으로는 `stage` 에서 검증된 변경만 병합한다. (예외: `hotfix/*`)

**MR(PR) 템플릿 항목**: 변경 요약 / 관련 이슈 / 대상 프로그램 ID / 변경 유형 / 테스트 결과 / DB 변경 여부(스크립트·롤백) / 설정 변경 여부 / 체크리스트(03 린트, 시크릿 없음, 06 리뷰 항목).

## 5. 버전 / 릴리스
| 항목 | 규칙 | 구분 |
|---|---|---|
| 릴리스 | 별도 `release` 브랜치 없음. **`main` 병합이 곧 릴리스** | 🔒 |
| 버전 규칙 | `MAJOR.MINOR.PATCH` (SemVer). MAJOR 호환 불가 변경 / MINOR 기능 추가 / PATCH 버그 수정 | 🔒 |
| 태그 | `main` 에서만 `v{MAJOR}.{MINOR}.{PATCH}` (예: `v1.2.0`). 저장소(프론트·백엔드)별로 독립 부여 | 🔒 |
| 릴리스 단위 | 소스 태그 + DB 스크립트 버전 + 설정 변경 목록 | 🔒 |
| 릴리스 노트 | 커밋 type(`feat`/`fix`) 기준 정리. 포함: 변경 기능, 프로그램 ID, 이슈, DB 변경, 영향 범위, 알려진 이슈 | 🔒 |
| 변경 이력 | `CHANGELOG` 를 릴리스 시 갱신 | 🔒 |
| 배포 주기 | 프로젝트별 정의 | ✏️ |

## 6. 환경 / 배포
### 6.1 환경 ↔ 브랜치
| 환경 | 약어 | 배포 기준 | 배포 방식 | 승인 |
|---|---|---|---|---|
| 개발 | dev | `develop` 병합 후 | **반자동 배포** (GitLab CI/CD 또는 Jenkins) | 불필요 (개발자) |
| 스테이지 | stg | `stage` 병합 후 | **반자동 배포** (GitLab CI/CD 또는 Jenkins) | 불필요 (개발자) |
| 운영 | prod | `main` 의 **태그** | 수동 배포, 승인 후 | **운영 배포 승인자** |
- **운영 배포 승인자와 롤백 결정자는 프로젝트 생성 계정**이다. 🔒
- **반자동 배포**: 코드를 `develop`(dev) 또는 `stage`(stg)까지 병합한 뒤, **개발자가 GitLab CI/CD 또는 Jenkins 의 배포 시작 버튼을 누르면** 자동으로 **빌드 → 도커 서버 배포 → 재기동**까지 수행한다. 병합만으로 배포되지는 않는다. 🔒
- prod 는 `main` 태그 기준으로 운영 배포 승인자의 승인 후 배포한다.
- 환경별 설정값은 소스에서 분리하고 시크릿은 저장소에 두지 않는다. (03 5.4)

### 6.2 운영 배포 절차 🔒
1. `feature/*` → `develop` 병합 → 개발자가 배포 시작 → dev 빌드·배포·재기동 및 개발 확인
2. `develop` → `stage` 병합 → 개발자가 배포 시작 → stg 빌드·배포·재기동, 검증 (06 테스트 기준 충족, 인수 확인)
3. 릴리스 노트·DB 스크립트·롤백 계획 준비
4. `stage` → `main` MR 생성 → **운영 배포 승인자 승인** 후 merge commit 병합
5. `main` 에 버전 태그 생성 → prod 수동 배포 (배포 윈도우 준수), 사후 점검(헬스체크, 로그 모니터링)
6. 배포 결과 기록·공유, `main` ↔ `stage` ↔ `develop` 동기화 확인

**배포 전 체크리스트**
- [ ] CI 전 단계 통과, 정적분석(시큐어코딩) 차단 이슈 없음
- [ ] stg 검증 완료
- [ ] DB 스크립트 검토 완료, **롤백 스크립트 준비**
- [ ] 설정 변경 목록 확인, 시크릿 반영 확인
- [ ] 영향 범위 공지, 롤백 담당자 지정
- [ ] 배포 윈도우: 프로젝트별 정의 ✏️

### 6.3 롤백 🔒
| 항목 | 규칙 |
|---|---|
| 롤백 기준 | 배포 후 사전 정의한 시간 내 치명 결함·장애 발생, 헬스체크 실패 |
| 결정 | **롤백 결정자 = 프로젝트 생성 계정** |
| 소스 롤백 | 직전 안정 태그를 재배포. `main` 정정은 별도 MR(`revert`) |
| DB 롤백 | 스키마 변경은 **롤백 스크립트를 릴리스와 함께 준비**. 데이터 변경(DML)은 사전 백업 후 적용 |
| 사후 | 원인 분석 및 재발 방지 기록, 필요 시 hotfix 진행 |

### 6.4 핫픽스 🔒
1. `main` 의 최신 태그에서 `hotfix/*` 분기 → 수정
2. `main` 으로 MR → **리뷰·승인 후 병합** (4장)
3. `main` 에 태그(PATCH 증가) → prod 수동 배포
4. `main` 을 `stage`, `develop` 에 역병합하여 동기화
- **긴급이더라도 사후 리뷰는 허용하지 않는다. 반드시 리뷰 후 머지한다.**

## 7. CI/CD 파이프라인
- **기본 도구는 GitLab CI/CD**이며, 필요한 경우 **Jenkins** 를 사용할 수 있다. 🔒
- 프론트·백엔드 저장소 각각 파이프라인을 둔다.

| 단계 | 내용 | 실패 시 |
|---|---|---|
| 1. 빌드 | 의존성 해석, 컴파일/번들 | 병합 차단 |
| 2. 린트·포맷 | 03 1장 포매터/린터 | 병합 차단 |
| 3. 단위 테스트 | 06 기준 | 병합 차단 |
| 4. 정적분석·시크릿 검사 | **Semgrep** 시큐어코딩 점검(03 5장), 시크릿 유출 검사 | 병합 차단 |
| 5. 패키징 | 배포 산출물 생성, 버전 부여 | |
| 6. 배포 | 도커 서버 배포·재기동. `develop`→dev, `stage`→stg 는 **개발자의 배포 시작 버튼**(반자동) / `main` 태그→prod 는 승인 후 수동 | |
- MR 마다 1~4단계를 실행한다. `develop`·`stage` 병합 후 개발자가 배포 시작 버튼을 누르면 빌드(5단계)와 도커 서버 배포·재기동(6단계)을 실행한다.
- 파이프라인 정의 파일은 저장소에 커밋한다. 배포 자격증명은 CI 시크릿 저장소에서 관리한다. (03 5.4)

### 7.1 저장소별 단계 명령 🔒
| 단계 | 백엔드 (Gradle) | 프론트엔드 (Vite) |
|---|---|---|
| 1. 빌드 | `./gradlew assemble` | `vite build` |
| 2. 린트·포맷 | `./gradlew spotlessCheck checkstyleMain checkstyleTest` | `prettier --check`, `eslint` |
| 3. 단위 테스트 | `./gradlew test jacocoTestReport` | `vitest run --coverage` |
| 4. 정적분석 | Semgrep | Semgrep |
| 5. 패키징 | Eclipse Temurin 기반 Docker 이미지 빌드 | 정적 파일 포함 Docker 이미지 빌드 |
| 6. 배포 | Docker Engine(또는 Kubernetes) 배포·재기동 | 동일 |
- 이미지 태그는 버전 또는 커밋 해시로 고정하고 `latest` 를 사용하지 않는다. 자세한 규칙은 03 8.2.

## 8. 이슈 관리
| 항목 | 규칙 | 구분 |
|---|---|---|
| 이슈 유형(라벨) | `feature`(기능) / `bug`(결함) / `change`(요구사항 변경, CR) / `docs` / `chore` | 🔒 |
| 우선순위 | `P1` 긴급(운영 장애) / `P2` 높음 / `P3` 보통 / `P4` 낮음 | 🔒 |
| 상태 | 신규 → 진행 → 리뷰 → 검증 → 완료 (반려/보류) | 🔒 |
| 연결 | 모든 브랜치·커밋·MR 은 이슈 번호와 연결 | 🔒 |
| 요구사항 변경 | `change` 이슈는 요구사항변경요청서(CR, 산출물 `00_03`)와 연결 | 🔒 |
| 결함 | 테스트 결함은 결함관리대장(06, 산출물 `04_01/99`)과 이슈 번호 연계 | 🔒 |
- 이슈 관리 도구는 GitLab 이슈를 기본으로 한다. 🔒
