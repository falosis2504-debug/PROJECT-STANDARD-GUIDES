## 3. 아키텍처 원칙
### 3.1 시스템 구성 🔒
```
[브라우저] ── 프론트엔드 (별도 저장소)
                │  HTTP (GET/POST) /api/{기능코드2}/{기능명}  · 세션 인증
            백엔드 (별도 저장소)
   Controller → Service → Mapper/Repository ── Oracle
                │
        [인터페이스: 별개의 시스템, IF 체계]  (연계 대상 시스템)
```
### 3.2 계층 구조 · 의존 방향 🔒
| 계층 | 역할 | 호출 가능 | 금지 |
|---|---|---|---|
| Controller | 요청 수신·검증·응답 포맷 | Service | Mapper/Repository 직접 호출, 업무 로직 |
| Service | 업무 로직·트랜잭션 경계 | Service, Mapper/Repository | Controller 호출 |
| Mapper/Repository | DB 접근 (SQL) | - | 업무 로직 |
| common / config | 공통 유틸·설정 | 모든 계층에서 사용 | 업무(기능코드) 로직 포함 |
- 의존 방향은 **Controller → Service → Mapper/Repository** 단방향이며, 역방향·계층 건너뛰기를 금지한다. (03 7장)
- **업무 로직은 애플리케이션(Service) 계층에서 처리**하고, DB 객체(함수·프로시저·패키지·트리거)는 필요한 경우에 한해 사용한다. (02 3.3)
- 트랜잭션은 Service 계층에서 시작·종료한다. (03 6장)

### 3.3 모듈 · 패키지 구조 🔒
| 원칙 | 내용 |
|---|---|
| 기능 단위 분리 | 기능코드 폴더(`IS`, `AM`, `CM`…) 아래에 역할 접미사 폴더(`Controller`, `Service`, `Dto`, `Mapper`…) (02 5.7) |
| 공통 모듈 | `common`, `config` 는 업무 폴더와 분리. 공통 코드 변경은 영향이 크므로 승인 후 반영 (00) |
| 프론트 구조 | 기능코드 폴더 바로 아래 파일 배치(역할 폴더 없음), `common`·`stores`·`routes` 등 공통 폴더 (02 5.7) |
| 기능 간 의존 | 다른 기능코드의 내부 클래스 직접 참조 금지. 필요 시 공통 모듈 또는 Service 인터페이스를 통해 호출 [제안] |
| 저장소 간 계약 | 프론트·백엔드는 **API 대장**(02 4.7)을 계약으로 하고 하위 호환을 유지 (05 1.1) |

### 3.4 API · 연계 원칙 🔒
- HTTP 메서드는 `GET`/`POST` 만 사용하고 동작은 기능명 동사로 표현한다. (02 4장)
- 응답은 공통 포맷을 사용하고 **업무 예외는 `exception`, 시스템 오류는 `E`+순번 코드**로 구분한다. (04 3장)
- 인터페이스(연계)는 **소스 체계와 별개의 시스템**으로 보고 IF 체계로 관리한다. (02-3)
- 대량·장시간 처리는 즉시 접수 후 비동기로 처리한다. (06 3.3.1)

## 4. 환경 구성
| 환경 | 약어 | 브랜치 | 용도 | 배포 방식 | 접근 |
|---|---|---|---|---|---|
| 로컬 | local | `feature/*` | 개발자 개발·단위 테스트 | - | 개발자 |
| 개발 | dev | `develop` | 통합 개발 | 반자동 (배포 시작 버튼) | 개발팀 |
| 스테이지 | stg | `stage` | 검증·인수·회귀 | 반자동 (배포 시작 버튼) | 개발팀·현업 |
| 운영 | prod | `main` 태그 | 서비스 | 수동, 운영 배포 승인자 승인 | 최소 인원 |
- 환경별 설정값은 소스와 분리하고, 시크릿은 저장소에 두지 않는다. (03 5.4)
- 환경 접근 주소·계정·서버 구성(서버 수, 사양)은 프로젝트별로 정의한다. ✏️
- 운영 데이터는 stg 이하 환경에 마스킹 없이 복제하지 않는다. (06 3.5)
