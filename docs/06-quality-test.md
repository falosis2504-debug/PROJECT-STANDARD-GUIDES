#### 3.3.1 업무 유형별 온라인 응답 시간(SLA) 구분 기준 🔒
| 업무 구분 | 권장 응답 시간 (API/화면) | 대표 업무 예시 | 핵심 특징 및 처리 방식 |
|---|---|---|---|
| **초단기 실시간** (인터랙션) | **0.1초 ~ 0.5초 이내** | 검색어 자동완성, 중복 확인(ID/닉네임), 장바구니 담기, 좋아요 | 사용자가 지연 없이 즉각적인 피드백을 기대하는 단순 조회·상태 변경 업무 |
| **일반 온라인** (표준 트랜잭션) | **1초 ~ 3초 이내** | 로그인, 마이페이지 조회, 상품 목록/상세 조회, 게시글 등록 및 수정 | 대다수 웹/앱 서비스의 기본 기준 (DB 인덱스 최적화 및 캐싱으로 3초 이내 방어 필수) |
| **복합 연동·결제** (외부 통신 포함) | **3초 ~ 10초 이내** | 카드 결제/계좌이체 승인, 본인인증, 외부 API 다중 호출 조회 | 외부 기관(PG사, 인증기관 등) 통신 지연 포함 (중복 클릭 방지 및 로딩 UI 필수) |
| **대용량·배치성** (비동기 처리) | **즉시 접수 응답 (1초 내)** (실제 완료: 수십 초~수분) | 대용량 엑셀 다운로드/업로드, 월말 정산 및 통계 집계, 대량 알림톡/이메일 발송 | 실시간 대기 시 타임아웃 발생 위험. 백그라운드 비동기 처리 후 완료 알림 방식 적용 |

#### 3.3.2 업무 유형 판단 요소
- **동기(Sync) vs 비동기(Async)**
  - 사용자가 결과를 확인해야 다음 단계로 진행 가능한 업무(결제, 로그인): **동기 처리 (최대 3~10초 내)**
  - 결과를 나중에 받아봐도 되는 업무(리포트 생성, 파일 변환): **비동기 처리**
- **외부 시스템 의존성**
  - 내부 DB 조회 중심 업무: **1초 이내** 목표
  - 타사 API 및 금융망 연동 업무: 네트워크 왕복 시간을 고려해 **5~10초** 수준
- **동시 접속 및 트래픽 집중도**
  - 선착순 이벤트, 수강신청, 티켓팅 등 순간 트래픽 집중 업무: 대기열 병목 방지를 위해 **0.5초 ~ 1초 이내**로 엄격히 제한

#### 3.3.3 타임아웃(Timeout) 설정 가이드
| 구분 | 기준 |
|---|---|
| API Gateway / 웹 서버 | 일반 온라인 업무 기준 **10초 ~ 30초** (무한 대기 방지) |
| 결제 / 외부 연동 | 데이터 정합성(망 취소 등) 문제 방지를 위해 외부 기관 권장 기준인 **30초 ~ 60초** 로 별도 분리 관리 |

- 각 API 는 위 기준표로 업무 유형을 분류하여 API 대장(02 4.7)에 **업무 유형과 목표 응답 시간**을 기록한다. 🔒
- 응답이 3초를 넘을 수 있는 업무는 중복 클릭 방지와 로딩 표시를 화면에 적용한다. (04 6.3)

### 3.4 인수 테스트
- 현업이 업무 시나리오로 수행하고 **인수확인서**로 승인한다. 인수 항목은 요구사항정의서와 1:1 추적된다. 🔒
- 인수 중 발견 결함은 4.1 등급 기준으로 처리하며 Critical/Major 잔존 시 운영 반영(05 6.2)을 보류한다. 🔒

### 3.5 테스트 데이터 🔒
- **운영 데이터를 테스트에 그대로 사용하지 않는다.** 개인정보·금융정보는 마스킹·가명 처리한 데이터를 사용한다. (03 5.3)
- 테스트 데이터 생성 스크립트(DML)는 소스 저장소에서 관리한다. (05 1장, 08 `01_DB_스크립트`)
- 테스트 계정·키는 시크릿 저장소에서 관리하며 소스에 커밋하지 않는다. (03 5.4)

## 4. 결함 관리
### 4.1 등급 / 처리 기준
| 등급 | 정의 | 처리 기준 |
|---|---|---|
| Critical | 시스템 중단, 데이터 손실·오염, 보안 취약점, 금융 거래 오류 | 즉시 수정, 해결 전 다음 단계·배포 불가 |
| Major | 핵심 기능 오동작, 우회 불가 | 다음 단계 진입 전 수정 |
| Minor | 부가 기능 오류, 우회 가능 | 일정 협의 후 수정 |
| Trivial | 표기·문구·UI 미세 오류 | 여유 시 수정 |
- 결함 SLA 는 위 **등급별 처리 기준을 현 기준으로 적용**하며, 별도의 수치 기한은 두지 않는다. 🔒

### 4.2 결함 처리 흐름 🔒
`등록 → 접수(검토) → 수정 중 → 수정 완료 → 재테스트 → 종료` (반려·보류·재오픈 가능)
- 결함은 **GitLab 이슈(`bug` 라벨)** 로 등록하고 결함관리대장(`04_테스트/01_통합테스트/99_결함관리대장`)과 번호를 연계한다. (05 8장)
- 결함 등록 항목: 제목, 등급, 발생 환경(dev/stg), 프로그램 ID, 재현 절차, 기대 결과/실제 결과, 로그 Trace ID(03 4.2), 첨부(화면·로그).
- 수정 커밋은 `fix({프로그램 ID})` 로 하고 `Refs: #이슈번호` 를 포함한다. (05 3장)

## 5. 단계별 종료(Exit) 기준 🔒
| 단계 | 종료 기준 |
|---|---|
| 단위 | 모든 케이스 수행·통과, 커버리지 목표 충족, 린트·정적분석 차단 이슈 0 |
| 통합 | 시나리오 100% 수행·통과, Critical·Major 결함 0건, Minor 잔존은 협의·기록 |
| 성능 | 성능 목표 충족 또는 승인된 예외 |
| 인수 | 인수확인서 승인, Critical·Major 0건 |
| 운영 반영 | 05 6.2 배포 전 체크리스트 충족, 운영 배포 승인자 승인 |

## 6. 코드 리뷰
### 6.1 리뷰 시점 (05 4장 연계) 🔒
| 시점 | 방식 |
|---|---|
| MR 생성 전 (`develop`, `stage` 병합) | **개발자 자체 점검**: MR 템플릿 체크리스트(6.3) 수행. 승인은 필요 없으나 CI 통과 필수 |
| `stage` → `main` MR | **승인 리뷰**: 운영 배포 승인자가 6.3 체크리스트로 검토 후 승인·병합 |
| `hotfix/*` → `main` MR | 승인 리뷰 필수. **긴급이어도 리뷰 후 머지**, 사후 리뷰 불허 |
- 승인 리뷰는 `stage` 대비 `main` 에 들어가는 **전체 변경분**을 대상으로 한다.
- 작성자가 프로젝트 생성 계정이면 본인이 6.3 체크리스트로 리뷰·승인할 수 있다. (00 2장)

### 6.2 리뷰 원칙 🔒
- 포맷 위반은 사람이 지적하지 않고 린터로 처리한다. (03 1장)
- 지적은 규칙(문서·조항)을 근거로 한다. 선호 차이는 규칙 변경 요청(00)으로 다룬다.
- 보안·DB 스키마·금융 거래 로직 변경은 리뷰 시 별도로 확인한다.

- [ ] 빈 catch·예외 삼키기·표준 출력 로그가 없다. 예외 원인을 보존했다
- [ ] 로그에 Trace ID·프로그램 ID가 있고 비밀번호·개인정보 원문이 없다
- [ ] 주석 처리된 코드·담당자 없는 TODO 가 없다. 업무 클래스 머리 주석에 프로그램 ID가 있다
- [ ] 매직 넘버·하드코딩 문구가 없고 공통코드/상수/메시지 파일을 사용했다

**설계 (04)**
- [ ] 응답이 공통 포맷이며 업무 예외는 `exception`(3.1.1), 시스템 오류는 `E`코드로 처리했다
- [ ] 목록 조회에 페이징이 있고 `SELECT *`·N+1 이 없다
- [ ] 화면 공통 기준(필수 표시·마스킹·버튼 배치)을 따랐다

**보안 (03 5장)**
- [ ] 서버측 입력 검증, SQL 바인딩 변수, 출력 이스케이프, 서버측 인가 검사가 있다
- [ ] 개인정보 암호화·마스킹, 시크릿이 소스에 없다

**테스트 · 형상 (05, 06)**
- [ ] 단위 테스트 포함(3.1), 커버리지 목표 충족
- [ ] DB 변경이 있으면 스크립트(`V{버전}__{설명}.sql`)와 **롤백 스크립트**가 있다
- [ ] 커밋 메시지·브랜치명이 규칙(05)을 따르고 이슈와 연결되어 있다
